## 3. B1 change and constraints

Added `backend/app/feasibility/readiness.py` with frozen `OperationalReadiness` and pure `assess_operational_readiness`. It accepts a server-supplied existing `Commitment`, optional `EvaluationSnapshot`, tenant scope and explicit aware evaluation time. It fails closed on absent snapshot, tenant mismatch, missing/conflicting current-version token, future capture and missing present-source evidence refs. It re-evaluates the existing P2 kernel at the supplied time, so source staleness, unknown inventory/capacity, BOM shortage, fixed bookings and allocation contention retain P2's semantics. Unsupported/missing target or multi-line mapping yields `UNKNOWN / UNSUPPORTED_OR_INCONSISTENT_INPUT`. Its only positive state is `READY_FOR_REVIEW`; `reservation_authorized` is structurally always false. No receipt parameter, SQL session, provider, writer, or Core command exists in this module.

The result's `assessment_id` is a deterministic **input identity**, not persisted assessment proof, a reservation receipt, source attestation, or acceptance token. `READY_FOR_REVIEW` means the supplied P2 facts evaluated feasible at that instant. Current-version token origin, source trust, verified actor, and transaction-time revalidation remain caller obligations; no authority should promote this object directly to `ACCEPTED`. A snapshot can change immediately after a read. The present-source evidence-ref check is only structural; even a nonempty ref is not verified business provenance. P2 remains responsible for actual missing/stale-source outcomes.

Added `backend/app/feasibility/tests/test_readiness.py`: deterministic positive projection and unchanged inputs, missing/current-version/tenant/future/provenance negative cases, stale sources, unknown capacity, shortage, competing allocation uncertainty, unsupported multi-line/missing target, naive clock, and rejection of a supplied receipt claim. The test uses the existing P2 fixtures; it introduces no second calculator. Tests inspect immutable inputs and the module has no writer/import path; no external database or provider was used. This proves no write in this evaluated code path, not a future integration path.

## 4. Reservation, concurrency and receipt assessment

The existing P3 `reserve_resource` conditionally increments reserved quantity only when stock remains available and uses a tenant-scoped idempotency key, with a unique database constraint. It records a P3 plan/action reservation. It does **not** atomically reserve all materials, production capacity and a pending OrderRequest, nor bind PR #48's terms hash, request version, snapshot and external operation ID. A local stock row and a synthetic `ev_res_*` audit ref cannot attest a live Orbyte reservation. Across workers, the Python lock is process-local; a future acceptance command needs database locking/version checks and an authoritative resource port with durable idempotent intent and receipt reconciliation. P2 readiness is a preflight only; its facts and terms must be re-read under the eventual decision boundary. Pending/unknown/failed receipts cannot cause an accepted Core transition.

PR #48's `ReservationReceipt` requires IDs/evidence for `CONFIRMED`, and `require_receipt_binding` compares tenant/order/operation/key/request version/hash. It does not independently verify provider signature, mode, inventory/capacity allocation, snapshot identity or that a receipt originated from the authoritative operation. The PR #48 reconciliation also found provenance and proposed-revision guard gaps in terms; Backend A/P5/P4 should resolve them on their branch. B1 does not label any receipt authoritative.
