# MouManTAI v2.2 Backend release audit — 24 October 2026

## A. Executive summary

**Verdict: NOT_READY for the complete v2.2 operational release.** The repository can demonstrate selected synthetic, explicitly isolated flows and several useful read-only decision aids. It cannot execute the required customer inquiry → durable OrderRequest → authorized SME acceptance → authoritative reservation → accepted Core Commitment → factual milestone journey through a single registered application path. Real Orbyte identity, inventory, reservation and joint P2 verification contracts remain unratified. The current public runtime uses header-based synthetic identity only when `MOUMANTAI_SYNTHETIC_MODE=1`, and otherwise fails closed. These are business integration gaps, not evidence that the pure modules are defective.

The most important work in this audit was preserving #69's four unique B/D/F/G/H and Foundation assertions in a focused test PR, reconciling and merging #39's synthetic PostgreSQL integration PR, and obtaining Backend review for the historical Wave 3 handoff. No live acceptance, supplier purchase, outbound communication, recovery execution or policy mutation was activated. The known OCR acceptance failure remains reproducible.

**Hackathon demonstration:** the isolated P1→Core→P2 supplier-delay→P3 persistence scenario is runnable on a migrated disposable PostgreSQL database. It is `SYNTHETIC_E2E_ONLY`; normal confirmed-event evaluation intentionally rejects its `synthetic://` source. The Frontend Orders queue defaults to an unavailable source, and decision reads explicitly refuse to infer v2.2 acceptance. Do not present a live end-to-end commitment or production Orbyte integration.

## G. Security and business authority

- `app/core/dependencies.py` requires synthetic mode for header-provided tenant/actor identity; default runtime returns `SYNTHETIC_IDENTITY_DISABLED`. Production-grade authentication remains unavailable. P1 paths additionally pass the `main.py` synthetic identity gate. Passing tenant-isolation tests within synthetic mode does not authenticate a live tenant.
- Core stores local state, audit and outbox together and has version/role/evidence checks. The legacy generic `/v1/commitments/{id}/transitions` can mutate synthetic agreement/fulfilment dimensions with role and supplied evidence refs; it is not the v2.2 exact-request/reservation command and must not be promoted as such. `/v1/backend-v2/terms/check` is explicitly synthetic and read-only.
- P2 evaluation and optimization remain read-only. `UNKNOWN`, solver unavailable and live verifier absence do not create feasibility or reservation authority. Real CP-SAT full-set contention is checked in `test_optimization.py`.
- Recovery's public Core execution dependency returns `None` and fails closed without durable authority. Isolated Recovery task execution requires the keyed mode and scoped approval; approval and execution have distinct records. Revalidation and idempotency have negative tests. No AI-initiated emergency action was enabled.
- Supplier quote, forecast, sent communication and decision history remain claims/derived observations until their own trusted evidence is bound. None is allowed to certify stock, customer assent, fulfilment or a policy update.
