# v2.2 Mock portfolio optimization follow-up

Stacked on PR #84. The registered `/v1/backend-v2/mock-optimization` API stores controlled synthetic Backend H `PortfolioRequest` and `P2ConstraintSpec` facts. Each candidate must be a fresh, reviewed PostgreSQL Mock OrderRequest with the same version, exact terms hash and revision, SKU/quantity/unit, deadline, verified received time and source identity. The comparison rechecks those bindings at read time. The native Backend H OR-Tools CP-SAT solver computes FCFS, profit and expiry scenarios. A synthetic verifier checks the entire selected portfolio's material allocations, lot availability/expiry, task schedules, resource windows and fixed-job contention before signing a fixture-only digest receipt.

Migration 0022 persists the immutable constraint dataset plus audit and outbox, following forecast history migration 0021. All input evidence refs must be `synthetic://`; responses are `DEMO-ONLY`, `SYNTHETIC`, and `operational_action_authorized=false`. The fixture has no P2 live authority. Its `accepted_reservations_protected` assertion is controlled Mock data, not a production stock guarantee. This route cannot reserve, accept, purchase or execute. Native OR-Tools is installed in the PostgreSQL CI job; an environment without it returns `SOURCE_UNAVAILABLE` rather than a fabricated scenario.

PostgreSQL HTTP tests exercise two registered inquiry/import/review routes, seed their exact bound portfolio constraint fixture, run native CP-SAT with full-set contention, audit/outbox, malformed/foreign source rejection, tenant/actor/production denial and later OrderRequest state invalidation. The existing Backend H pure tests remain the detailed solver regression suite. This is still an advisory Mock workflow; decision-memory API and accepted-order P3/P4 event links remain outstanding.
