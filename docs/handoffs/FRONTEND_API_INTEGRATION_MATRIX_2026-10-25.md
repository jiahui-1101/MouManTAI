## Approval boundary and narrow proposal

The `/v1/backend-v2/*` contract explicitly requires `X-Isolated-E2E-Key`, server-configured manager identity and a single configured tenant. Its handoff requires a backend-for-frontend or trusted local proxy before React can invoke it. A browser-supplied header or Vite `VITE_*` secret would turn a server credential into a public browser credential. The existing Vite proxy only forwards this credential for selected Recovery and P4 operations; it does not authorize OrderRequest use. Extending it to all `/v1/backend-v2` routes would expose privileged fixture creation and business commands. Request P5/Orders owner review for a narrow server-owned, authenticated, tenant-bound OrderRequest read/review/accept/status/timeline facade, with method/path allowlisting, manager verification, CSRF protection, and no client-visible key. The existing endpoint DTOs and version/idempotency semantics can remain unchanged.

Main's #95 PostgreSQL HTTP/worker test demonstrates an isolated same-Commitment path through accepted OrderRequest, P2 impact, P3 approval/execution receipt, P4 pending intent and timeline. It is not Browser E2E evidence. P1 inbound is not automatically converted to the Mock OrderRequest and C2 real provider transports are not connected to P4 authorization. Staging GO/NO-GO: **NO-GO for the requested frontend end-to-end journey** until the trusted authority boundary is approved and implemented, then tested in a browser against PostgreSQL 16 and the worker.
