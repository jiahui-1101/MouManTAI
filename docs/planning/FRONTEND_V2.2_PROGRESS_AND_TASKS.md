**Audit date:** 2026-10-23. **Scope:** frontend only; no application changes in this audit. Sources: [frontend requirements](../requirements/v2.2/REQUIREMENTS_FRONTEND.md), [system requirements](../requirements/v2.2/REQUIREMENTS_SYSTEM.md), [backend target contracts](../requirements/v2.2/REQUIREMENTS_BACKEND.md), [Orbyte design system](../design/ORBYTE_DESIGN_SYSTEM.md), current routes/components/tests and Git history. ## Snapshot

**Estimated confirmed v2.2 frontend completion: ~30% (±10 percentage points).** This is an effort-weighted planning estimate, not a passing acceptance score: the shell and legacy P1–P5 detail workflows are substantial, but the message → reviewed order → guarded acceptance/reservation → milestone → fulfilment journey cannot yet run end to end. No whole v2.2 requirement below is marked COMPLETE; several reusable sub-capabilities are complete for their existing contracts. Remaining confirmed/design-review frontend work is approximately **261 developer-hours**, conditional on backend contracts and test data arriving. Proposed scope is excluded from that estimate.

**Status key:** PARTIAL = real reusable implementation, incomplete v2.2 scope; MISSING = no corresponding routed UI; BLOCKED = required authoritative backend data/command is not present in inspected routes (UI may be prepared but cannot truthfully finish); PROPOSED = future scope, outside the confirmed estimate. A BLOCKED row may also have partial legacy UI.

## Backend/API gates and execution rules

The inspected FastAPI routers expose real `/v1/messages`, `/v1/contexts`, `/v1/commitments`, P2 commitment assessments/impacts, `/v1/recovery`, `/v1/communications`, `/v1/confirmations`, `/v1/overview` and `/v1/audit`. The v2.2 backend document §14 names **target** conversation/issue/review, order/acceptance/portfolio, calendar, status/feedback/daily-summary, supplier/offer/comparison/selection and incident queue APIs; these were not found as deployed routes. Agree typed contracts, authorization, tenant scoping, version/error semantics and test fixtures with backend owners before enabling commands. The existing P2 assessment route is for **confirmed commitments** (`backend/app/feasibility/router.py:184`), so it cannot stand in for pending-order acceptance. Recovery approve and execute are already separate server commands (`backend/app/recovery/router.py:332,389`). Orbyte membership/switch, live provider credentials and Replit reply endpoint remain unverified external contracts; show the current tenant only and disclose connection modes. Backend, not the frontend, must validate reservations, consent, approval and fulfilment.

## Allocation of remaining confirmed/design-review work

Estimates include feature-level tests and integration review, exclude backend build time and PROPOSED pages. Developers should branch from a common committed baseline after deciding what to do with the pre-existing uncommitted shared UI/test changes. A owns customer/communications feature folders; B owns orders/feasibility/calendar; C owns supplier/recovery/overview/activity plus **all** `App.tsx`, `layout/`, `shared/` and navigation integration edits. A/B add feature-local API modules and export page/panel contracts; C registers routes and shared primitives in one integration pass. B owns the order-detail composition; A supplies message/status panels through exported components, avoiding concurrent edits to that page. Existing deep links remain regression requirements.

**Implementation order:** (1) Confirm backend route/response availability and design-review semantics for exact terms, portfolio proof and one-click recovery approval; freeze feature-local types and IDs. (2) In parallel, A builds inquiry/clarification/review on real data, B builds pending order/detail/guarded decision on real data, C builds supplier/recovery and owns shared primitives. (3) Wire A's panels into B's order detail, then C adds routes/nav links only when destinations work; preserve legacy paths. (4) Add calendar, milestones/feedback, daily performance and cross-feature Activity once authoritative events exist. (5) Run `FE-UAT-01..08,10,12..15` end to end with tenant/role/conflict/error cases; then revisit the ~30% estimate. RFQ, forecasting, decision memory, broad incident expansion, full business settings and proposed command-center aggregation stay in a separate backlog until product signoff and verified APIs.
